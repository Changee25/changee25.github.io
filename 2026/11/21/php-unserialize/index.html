1.反序列化漏洞

程序把不可信输入当作序列化数据来反序列化，攻击者借此控制“实例化哪个类、给属性赋什么值”，再让程序自己触发的魔术方法（__destruct、__wakeup、__toString…）执行恶意逻辑，最终实现任意文件写入、任意命令执行、SSRF 等。

产生条件

  1. 应用程序使用unserialize() 函数处理用户输入
  2. 输入数据未经过充分验证
  3. 存在可利用的魔术方法或对象方法调用链

魔术方法

按用途分类五组：

1. 生命周期
方法 触发时机
__construct() new 创建对象时
__destruct() 对象销毁时（脚本结束、unset、引用计数归零）
__clone() clone 对象实例时（在副本上调用）
2. 属性访问拦截
方法 触发时机
__get() 读取不存在或不可访问的属性
__set() 写入不存在或不可访问的属性
__isset() 对不可访问或不存在属性做 isset() / empty()
__unset() 对不可访问或不存在属性做 unset()
3. 方法调用拦截
方法 触发时机
__call() 调用不存在或不可访问的实例方法
__invoke() 把对象当函数用
4. 字符串化与调试
方法 触发时机
__toString() 对象被当字符串用
5. 序列化专用

只有调用 serialize() / unserialize() 时，引擎才会自动调用它们

方法 触发时机 备注
__sleep() serialize() 前 返回要序列化的属性名数组
__wakeup() unserialize() 后 反序列化后立刻调用
__serialize() serialize() 时 PHP 7.4+，优先于 __sleep
__unserialize() unserialize() 时 PHP 7.4+，优先于 __wakeup

2.POP链

从这里开始可能有点乱

Property-Oriented Programming Chain

pop链（Property-Oriented Programming Chain,面向属性编程链）是反序列化漏洞利用的核心技术，核心思想是通过控制对象的属性值，引导程序执行流经过多个类的调用，最终触发危险动作。

在不注入任何自定义代码的前提下，攻击者利用目标应用中已存在的类（称为 gadget）及其魔术方法，通过对反序列化对象图（object graph）中属性值的精确控制，构造出一条由引擎自动触发的调用链，从某个入口魔术方法出发，经由若干 个类逐级转发，最终到达危险操作。

这个有点像多米诺骨牌吧，程序里本来就有很多牌（方法），反序列化让我们能把牌摆成一条线，这个时候只需要推倒第一张（触发 __destruct）就可以让最后一张正好落在“执行命令”上。

步骤：

  1. 寻找可利用的魔术方法作为起点
  2. 找到危险函数或操作作为终点
  3. 构建方法调用链，链接起点和终点

pop链是怎样被构造出来的

实战里是“反向找路”：

  1. 找入口：全局搜索 __destruct / __wakeup / __unserialize（这些必定触发）。
  2. 找出口：搜索 sink（汇聚点，意思就是最后造成危害的函数调用）——shell_exec、system、eval、include、file_put_contents、unserialize（二次）、curl_exec。
  3. 连边：从出口往回找“谁能以可控参数调到 sink”，再看这个点上有没有 __toString/__call/__get 之类的魔术方法可以接力；一路倒推到入口。
  4. 验证：本地把对象图 serialize() 出来，实际跑一遍，看链是否通。

pop快速构析

正常情况下的反序列化：

反序列化开始 → 生成对象 → 执行 __wakeup → 反序列化结束，赋值 → … → 脚本结束，执行 __destruct。

利用fast_destruct：

反序列化开始 → 解析出错/拒绝赋值 → __wakeup 被跳过/中断 → 异常对象被立刻当作垃圾回收（GC） → 瞬间触发 __destruct。

__destruct 的触发时机取决于“最后一个引用消失”，而非“脚本结束”；快速析构就是人为让那一刻提前到来。

5.gc回收

First.先说它要解决什么问题

看这段代码：

删了吗？并没有。

因为 a 说“b 还拿着我呢”，b 说“a 还拿着我呢”。两个都以为“还有人再用”，结果谁也没有被删。

gc回收就是专门抓这种“互相拿着、谁都不放手”的东西。

PHP 平时是怎么删东西的

平时不需要垃圾回收。PHP 给每个数据记了一个数：“现在有几个人拿着我”。

  • 有人拿着 → 数字加一
  • 有人放手 → 数字减一
  • 减到零 → 立刻删掉（顺便执行它的“遗言” __destruct）

这套办法又快又准，绝大多数情况够用。唯独遇到“互相拿”就失灵了——数字永远是 1，永远不归零。

垃圾回收怎么发现“互相拿”？

有人会想：挨个检查所有数据不就行了？

nonono 程序里可能躺着几百万个数据，每个都查一遍，性能就崩了。

PHP 的做法很取巧：只查“最近有人松过手”的那些。

因为想想就知道：

  • 从来没人松过手 → 说明一直有人正常用着，不可能是垃圾
  • 一松手就归零了 → 已经删了，不用管
  • 松过手、但还是没归零 → 嫌疑最大，可能就是“外面的人都走了，只剩内部互相拿着”

这些“嫌疑对象”会被记在一张名单上。名单攒到大约一万个，才出动一次全面检查。

检查的办法

假设名单上这批对象，全都可能是垃圾。那怎么验证？

第一步：先假装它们全是垃圾。

把每个对象的“人数”都偷偷减一。这等于告诉系统：“先别算它们内部互相拿的那一份。”

第二步：看看谁还剩人数。

  • 还剩大于零 → 说明名单外头还有真人拿着它，它是活的，放回去，不算垃圾。
  • 已经减到零 → 说明它的引用全在这批名单里，外面没人要了，纯纯的互相锁死。

第三步：清掉该清的。

第二步里减到零的，就是真正的垃圾，删掉，并执行它们的“遗言”。

就这么简单：先假设全是垃圾，再看谁还能证明自己活着，剩下的清掉。

什么时候会检查
时机 说明
名单攒满（约一万个） 自动检查一次
手动叫 gc_collect_cycles()
程序结束 强制全部清理，不管有没有环
跟反序列化有什么关系

先说一下几个常见的环

1. 有环，析构就会“迟到”

2. 想“立刻执行”，就别造环

如果希望 __destruct 在反序列化后马上跑（快速析构），那 payload 里千万别用 r: 造自引用。一造环，就变成“等清洁工来”了。

3. 想“晚点执行”或“保活”，就故意造环

有些链需要对象活到所有业务代码跑完，甚至活到程序结束——那就故意让它进环。

4. 别人手动叫清洁工的时机，可能是我们的引爆点

如果目标程序里有 gc_collect_cycles()（队列、长驻进程里常见），那我们析构可能就在那一刻被触发。

5. 环还能撑爆内存

大量环对象不释放，内存一路涨，这是一种拒绝服务。

6.session反序列化

本质是：session_start() 会自动反序列化 sess_xxx 文件，而 php 与 php_serialize 两种 handler（处理器）对 | 的处理不一致——攻击者先通过某个业务功能把 |O:... 写进 session，再让另一个使用不同 handler 的页面去读，就完成了一次“不需要写 unserialize() 的对象注入”。

session.serialize_handler 是“会话序列化处理器”，负责决定 session 数据以什么格式打包和解包——选 php 就用 键|值 的格式，选 php_serialize 就把整个数组一起序列化。

session 怎么存

session_start() 之后，PHP 会：

  1. 从 Cookie 里拿 PHPSESSID
  2. 去 session.save_path 指定的目录找 sess_<id> 文件
  3. 把文件内容反序列化，还原成 $_SESSION 数组
  4. 请求结束时，再把 $_SESSION 序列化写回文件

关键在第 3 步：session_start() 内部就在做反序列化。这就是入口——代码里看不到 unserialize()，但它确实发生了。
