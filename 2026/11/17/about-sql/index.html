第三次例会-sql注入

1. SQL 注入的原理与成因

定义：用户输入被拼接进 SQL 语句文本，被数据库解析器当作语法结构执行，而不是当作数据处理。

成因分三层，缺一不可：

层次 内容
① 语言层 SQL 是以字符串形式构造的语言，语句本身就是一段文本
② 构造层 用字符串拼接把用户输入放进这段文本，输入因此获得了成为语法的机会
③ 解析层 数据库只收到拼接完成后的最终字符串，无从分辨哪几个字符来自程序、哪几个来自用户

为什么会产生歧义（数据与代码混淆）？

关键在于来源信息在拼接的那一刻就永久丢失了。数据库拿到的是一串字节，它只有一个视角：按 SQL 语法解析。它没有”这段是用户给的值”这个信息，因此：

一旦用户输入里含有 '，它就能关闭程序打开的字符串上下文，让后续字符落到语法区。

——>歧义的本质：同一段字节既可被解释为数据、也可被解释为代码，而解释器只做一种解释。

这一句话同时解释了 XSS（HTML 解析器）、SSTI（模板引擎）、命令注入（shell）——同一族缺陷，只是解释器不同。

万能密码

通过注入把登录语句的 WHERE 条件改写成恒真，让程序以为”密码验证通过了”。
它由三个部件拼成

部件 干什么
① ' 关掉服务端开的引号，从”数据”跳进”语法”
② OR 1=1 造一个永真条件，让 WHERE 对所有行都成立
③ --+ 把 AND password=... 作废
两个漏洞叠加
  1. 拼接：值参与了语句构造判定偷懒：程序拿”查询有返回行”当作”认证通过”

OR 1=1 是恒真，恒真的后果是全表都返回，而 fetchone() 只取第一行。

⇒ 所以”想指定登进 admin”，靠的其实是 admin' --+（只闭合 + 只注释），不是靠 OR 1=1。

OR 1=1 管”条件永真”，-- 管”锁定账号”，这俩是两件事。

三个失效条件
  • 参数化查询（占位符，值在语法树定型后才填）→ 完全无效
  • 密码哈希在应用层比对（bcrypt/argon2 的 checkpw）→ 即使返回多行也过不去，因为明文密码攻击者没有
  • 额外的账号状态 / 验证码 / 限流校验 → 拿不到会话

危险的根源不在”拼了字符串”，在于”用户输入进入了语句文本”。

本质区别是时序

⇒ 预编译的防护力不来自”过滤了什么字符”，而来自”值与语法在时间上被分开了”。 值只能填进预留的数据槽，没有机会改变语句结构。

三个注意点：

  1. 占位符不是字符串替换的语法糖(为了让代码好写而提供的简写，它不增加任何语言能力，总能等价展开成原本的写法。)，它是语法树(文本被解析后得到的树形结构)上的一个洞。

  2. execute("... %s" % x) 不是参数化——% 是 Python 的字符串格式化，在发给数据库之前就把值塞进文本了，数据库完全不知道这里原本有占位符。判据很简单：execute 有没有第二个参数。

  3. 拼接本身不危险。若拼进语句的是代码里的常量（例如白名单映射后的列名），依然安全。危险只发生在”用户输入进入语句文本”时。

3. 什么是引号闭合，为什么必须闭合

定义：SQL 用引号界定字符串字面量（'...' 单引号字符串，"..." 在多数库中是标识符，MySQL 反引号 ` 是标识符）。当参数被写在引号内部时，注入的第一个动作必须是关掉那个还开着的引号，才能把执行流从”字符串上下文”搬到”语法上下文”。

为什么必须闭合？ 因为不闭合的话，我们写的一切都只是字符串的内容：

⇒ 闭合是注释的前提。

要闭合什么，取决于参数在语句里的包裹形式：

服务端写法 需要闭合 有效前缀示例
WHERE id=$x 无（数字型没有引号） 2
WHERE name='$x' ' 2'
WHERE name="$x" " 2"
WHERE id=('$x') ') 2')
WHERE id=(("$x")) ")) 2"))
WHERE t LIKE '%$x%' %' x%'

括号为什么也要闭合？ 因为括号是语法分组符，开着的括号不关上，整条语句无法通过解析——数据库会直接报语法错误，注入根本不会执行。

规律：

payload 结尾的符号序列 = 服务端参数左侧悬空符号的镜像。 数一下参数左边有几个没关的引号/括号，就写几个”关”的动作。

不闭合的行不行？ 行——用配对闭合代替注释：' OR '1'='1，让引号自己成对，整条语句依然合法。这证明”闭合”与”注释”是两个独立部件。

4. UNION 为什么要匹配列数

因为 UNION 的语义是”把第二个结果集纵向接在第一个下面”。 结果集是一张二维表，两张表要上下摞成一张，栏数对不齐就没法装订。
所以列数不等时报错发生在解析/优化阶段——根本没执行，既拿不到数据也拿不到回显：

探测列数两条路：ORDER BY n 递增到报错、UNION SELECT NULL 逐个加到不报错。
⚠️ 为什么必须用 NULL 探：NULL 能适配任意列类型。如果用数字或字符串探，分不清报错是”列数不对”还是”类型不对”——一次只验一个变量。

5. 什么叫回显位

SQL 可以返回 N 列，但页面通常只把其中某几列的值渲染出来。被真正显示出来的那一列，就是回显位。
它决定成败：数据塞进不回显的列 = 竹篮打水一场空，数据确实在查询结果里，但你在页面上看不见。
找法：UNION SELECT 1,2,3 填可辨识标记，页面出现哪个数字，那一列就能用。
❗原查询必须先返回空（id=-1 / AND 1=2），否则 UNION 行排在后面，页面首行仍是原始数据
类型不兼容（数字列塞字符串，MySQL 可能隐式转换或报错）
列表页可能渲染多行，取第几行的策略不同

  • 列:哪个格子会被显示 → 回显位 页面渲染代码决定

  • 行:第几行被取走 → 万能密码里”登进谁” fetchone()决定

6. 布尔盲注为什么能逐字符拿到信息

页面不回显数据，但它有两种状态（正常 / 异常）—— 那就是一根只有 1 bit 宽的信道。我们要做的是把”数据是什么”翻译成”数据库能回答真或假的问题”：

为什么必须逐字符：SUBSTRING(x,i,1) 每次只截一个，保证”这一次问只涉及一个字符”——否则一次改动牵动多个变量，读到的 bit 归不到具体字符上。又是一次只验一个变量。
为什么要二分：一个字符约 95 个可打印取值，线性扫要几十次；二分 log₂95 ≈ 6.6 → 约 7 次请求锁定 1 个字符。库名 10 字符 ≈ 70 次请求，这就是盲注慢的原因。
成立前提：页面必须有稳定可区分的两种状态。

8. 注释后续 SQL 的目的 · 各数据库注释符

目的

闭合之后，原语句尾部还剩下内容（如 ' AND pass='...'、LIMIT 1、ORDER BY x）。这些残留会造成两种后果：

  1. 语法错误——引号/括号不配对，语句直接被拒
  2. 逻辑抵消——例如残留的 AND pass='xxx' 让 OR 1=1 白写，条件仍然为假

所以要用注释作废尾部，让语句在我们想要的位置结束。

URL 编码要点

符号 必须写成 原因
# %23 # 在 URL 中是 fragment 分隔符，裸写会导致其后内容根本不发给服务器
-- 的空格 %20 或 + MySQL 要求 -- 后必须有空白；+ 在 query 中会被解码成空格，所以 --+ 是最常见写法
空格 %20 裸空格不合法，且尾部空格常被中间层 trim 掉

MySQL 为什么严格要求 -- 后跟空白？ 因为 --1 这类写法会被解析为”减 1”或负号，只有 -- 1才是注释。

或者不用注释，改用配对闭合：' OR '1'='1 —— 全程引号成对，无需作废任何尾部。

9. SQL 注入的类型与分类

A. 按数据回传通道（最常说的”注入类型”）

类型 成立条件 典型手法
联合查询 UNION 页面有回显位 UNION SELECT 取数据；约束：列数必须相同、类型需兼容
报错注入 Error-based 错误信息会回显 MySQL：updatexml/extractvalue（XPath）、floor(rand()) 主键冲突、exp() 溢出；MSSQL：convert/cast 类型转换报错；Oracle：UTL_INADDR、ctxsys.drithsx.sn；PG：cast 报错
布尔盲注 Boolean-blind 页面存在两种可区分状态 AND 1=1 vs AND 1=2；AND ASCII(SUBSTRING(x,i,1))>N 逐位二分
时间盲注 Time-blind 页面完全无差异 MySQL SLEEP(n)/BENCHMARK；MSSQL WAITFOR DELAY；PG pg_sleep(n)；Oracle DBMS_PIPE.RECEIVE_MESSAGE；SQLite 无内置 sleep，用 RANDOMBLOB 构造耗时
带外 OOB 结果不回传但能出网 MSSQL xp_dirtree、Oracle UTL_HTTP/UTL_INADDR、MySQL LOAD_FILE + UNC 路径（Windows），数据经 DNS/HTTP 外带到自己的服务器
堆叠查询 Stacked 驱动允许多语句 ; 后接新语句，可执行 INSERT/UPDATE/DELETE。PHP 的 PDO 默认不允许多语句，mysqli 需 mysqli_multi_query；MSSQL/PG 支持较好

B. 按注入点在语句中的形态

形态 特征
数字型 参数不在引号内，无需闭合——这也是”过滤单引号”防御失效的原因
字符型 需闭合引号
搜索型 LIKE '%...%'，需闭合 %'
ORDER BY / GROUP BY 后 标识符位置，不能参数化；常需白名单，或用子查询 + 时间盲注探测
LIMIT / OFFSET 后 部分驱动支持绑定，行为不统一，通常强转 int + 范围校验
INSERT / UPDATE 中 一般无回显，多用报错注入或时间盲注
表名 / 列名位置 标识符，只能白名单

C. 按输入来源（HTTP 位置）

GET 参数、POST body、Cookie、以及各类 HTTP 头：User-Agent、Referer、X-Forwarded-For、Accept-Language。

⚠️ XFF 注入的典型场景：服务端把 X-Forwarded-For 当作”访客 IP”写进日志表，且写入时用了拼接。

D. 按触发时机

  • 一次注入：输入当次即进入语句
  • 二次注入（Second-order / Stored）：恶意数据先被存进库（入库时可能还做了转义），之后被取出再拼进另一条新语句时才触发。
    经典形态：注册用户名填 admin'--，后台”修改密码”逻辑是 UPDATE users SET pass=... WHERE username='$stored_name' → 存的时候无害，取出来用时爆发。
    ⇒ 过滤发生在入库前，不等于安全；危险发生在”取出来再拼接”的那一刻。

E. 按编码/字符集绕过

  • 宽字节注入：GBK 等双字节字符集下，转义函数插入的 \（0x5C）会与前一个字节（如 %DF）合成一个合法双字节字符（運），使原本被转义的引号”逃逸”出来。
    成立条件：连接字符集为 GBK + 使用 addslashes/mysql_real_escape_string + 未开启 NO_BACKSLASH_ESCAPES。
  • 其他：URL 双重编码、Unicode 归一化、注释拆分关键字（UN/**/ION）、大小写混写、MySQL 版本条件内联注释 /*!50000 ... */。

10. SQL 注入能造成什么危害

一旦注入成立，攻击者拥有的能力 = 数据库账号拥有的能力。

类别 具体能力 前置条件
读取 全库数据（拖库）、跨库数据 相应库表的 SELECT 权限
服务器文件 MySQL LOAD_FILE()；MSSQL xp_cmdshell/OPENROWSET；PG COPY ... FROM；SQLite readfile()（需扩展）
篡改/破坏 UPDATE/DELETE 改数据、DROP 删表 相应权限；DROP 通常还需堆叠查询
认证绕过 ' OR '1'='1 直接登录后台 登录逻辑用拼接
写文件 → getshell MySQL INTO OUTFILE/INTO DUMPFILE 写 webshell FILE 权限 + secure_file_priv 允许该路径 + 知道 web 根目录 + 该目录可写且能解析
命令执行 RCE MSSQL：xp_cmdshell、sp_OACreate、CLR 程序集、Agent Job xp_cmdshell 在 2005+ 默认禁用，但可 sp_configure 开启（需相应权限）
MySQL：UDF 提权（写 .so/.dll 到 plugin_dir 后 CREATE FUNCTION → sys_eval） FILE 权限 + plugin_dir 可写
PostgreSQL：COPY ... PROGRAM、PL 语言（plpython/plperlu）、lo_export COPY ... PROGRAM 需超级用户（9.3+）
Oracle：UTL_FILE、Java 存储过程、DBMS_SCHEDULER 相应权限授予
SQLite：load_extension() 加载动态库、ATTACH DATABASE 写文件 扩展加载未被禁用（多数语言绑定默认禁用）
提权与横向 读 mysql.user 拿账号哈希、读其他系统凭证、以数据库服务器为跳板进内网 数据库常部署在内网，且往往权限过高
拒绝服务 删表、构造超长耗时查询、BENCHMARK() 打满 CPU —
信息泄露 版本号、绝对路径、账号名、表结构 → 为后续攻击铺路 报错回显或 UNION 回显

11. 数据库最小权限为什么重要

因为它控制的不是”会不会被注入”，而是”注入之后的爆炸半径（blast radius）。

注入漏洞决定攻击者能不能执行 SQL；数据库权限决定这条 SQL 能做到什么。

为什么必须有这一层

纵深防御的前提假设是：上层迟早会被绕过。 现实中的绕过点很多：

  • WAF 本质是基于规则的字符串/语法匹配，绕过面永远存在
  • 参数化覆盖不到标识符位置（ORDER BY、表名、列名）
  • ORM 的原生查询逃生舱（raw()、extra()、text()、MyBatis ${}）
  • 存储过程内部的动态 SQL
  • 二次注入（入库时安全，取出时拼接）

具体收益对照

收回的权限 直接切断的攻击路径
FILE LOAD_FILE 读系统文件、INTO OUTFILE 写 webshell → 切断 SQLi 通往 RCE 的那座桥
SUPER / sys 改配置、开启 xp_cmdshell、创建 UDF
DROP / ALTER 破坏表结构（从”数据被偷”升级为”数据被毁”）
GRANT OPTION 攻击者给自己提权、留持久后门
跨库全局读 从”泄露一个业务库”放大成”拖走整台实例所有库”

实践清单

  1. 业务账号只授指定库、指定表的 SELECT/INSERT/UPDATE/DELETE
  2. FILE、SUPER、DROP、GRANT、PROCESS 一律不给
  3. 读写分账号：只读接口用只读账号，泄露了也改不了数据
  4. 备份、迁移、管理各用独立账号，与业务账号分离
  5. MySQL 设死 secure_file_priv（指向一个 web 不可达目录，或设为 NULL 彻底禁用文件读写）
  6. 数据库服务进程不要用 root / Administrator 运行
  7. 数据库服务器不放公网，只允许应用服务器 IP 访问

搜索框 LIKE '%kw%' 常整段拼接，且开发时只测正常关键词
登录 / 注册 认证绕过（' OR '1'='1）+ 二次注入的经典源头（用户名被存下，后续被拼接使用）
后台管理功能 增删改查、批量操作、筛选、导入导出；常被误认为”内网/需登录所以安全”而防护最弱
表单隐藏字段 开发者以为用户看不到就不会改，实际可任意篡改
Cookie 会话里存的用户 ID、偏好、购物车序列化数据
HTTP 头 User-Agent（写访问日志）、Referer、X-Forwarded-For（记 IP）、Accept-Language
文件名 / 路径参数 上传后记录原始文件名，文件名里带 ' → 典型二次注入
分页参数 LIMIT / OFFSET 常被强转失败或直接拼接
RESTful 路径段 /user/123 里的 123
JSON / XML body 字段 结构化数据里的某个字符串字段
报表与导出的筛选条件 条件复杂，常绕过统一的参数化封装

容易被”以为安全”的地方（真实项目高频成因）

  1. ORM 的原生查询逃生舱：Django raw() / extra()、SQLAlchemy text()、Sequelize literal()、JPA createNativeQuery() 拼接
  2. MyBatis ${} vs #{}：${} 是字符串直接替换（等于拼接，可注入），#{} 是预编译参数绑定（安全）。这是国内 Java 项目最高频的真实成因
  3. 动态表名 / 列名 / IN (...) 列表：占位符绑不了标识符，IN 的元素个数也不能绑定 → 常被拼接
  4. 存储过程内部的动态 SQL：调用方参数化得再干净，过程体里 EXEC(@sql) 拼一次，注入立刻回来
  5. 二次注入：入库前做了转义，取出来拼新语句时没做
  6. 延迟触发的路径：定时任务、消息队列消费者、异步作业——数据来源是用户输入，但触发时间延后，代码评审时容易漏
  7. 缓存层 / 搜索层：为了拼查询条件而绕过了 DAO 的参数化封装

审计方法

追数据流，看 sink。 从每个外部输入（request.args、request.form、headers、cookies、上传文件名、消息体字段）出发，一路跟到数据库调用点，检查两点：

  1. 这个值是否以字符串拼接/格式化的方式进入了 SQL 文本？
  2. 若进入的是标识符位置（表名、列名、ORDER BY），是否走了白名单映射？

只要①为是且②没有白名单，就是注入点——与它在页面的哪个角落无关。

任何防御只有覆盖”必经路径”才有效；一切绕过的本质，都是走了一条没被防守的路。
参数化是唯一改变”值与语法何时相遇”的机制，所以它是必经之路；
过滤引号拦不住数字型，转义拦不住宽字节与二次注入，WAF 拦不住编码变体——它们都是可选支路。

?. MYSQL植入Webshell

把 MySQL 当作“文件写入器”，把一段脚本写到 Web 服务器能解析的目录里，从而把 SQL 注入升级成远程命令执行（RCE）

三条主流路径

① INTO OUTFILE / INTO DUMPFILE（写马）

  • OUTFILE 会转义 \、换行、制表符，所以代码里有反斜杠会被破坏；DUMPFILE 是原始写入、只允许单行单列，适合一句话或二进制。
  • 目标文件必须不存在，否则报 “already exists”。
  • 内容里的引号用十六进制或 CHAR() 规避。

条件：通过 数据库权限层 → 文件系统层（知道绝对路径） → Web 执行层 三关

② 日志写马（general_log）——OUTFILE 被 secure_file_priv 挡住时的常用替代：

需要 SUPER / SYSTEM_VARIABLES_ADMIN，且 log_output=FILE。slow_query_log 同理（把 long_query_time 设为 0）。副作用大、日志量暴增，通常打完立刻关。

③ UDF 提权——不是“Web 马”，而是直接执行命令：把 lib_mysqludf_sys.so 通过 INTO DUMPFILE 写进 plugin_dir，再 CREATE FUNCTION sys_eval RETURNS STRING SONAME 'lib_mysqludf_sys.so'。它需要文件写权限 + CREATE FUNCTION 类权限，属于同一套“文件写”能力的延伸。
